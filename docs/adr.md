# agenteval 设计决策记录（ADR）

> 本项目回答"eval pipeline 怎么搭/judge 可信吗/怎么防回归"——每条决策对应模块与真实数字。

## ADR-1 为什么自研而不接 Langfuse/RAGAS

- **背景**：市面上评测工具很多，自研的理由必须能扛住"为什么不用现成的"。
- **决策**：自研 judge 校准（对人工标注算 kappa）、CI 回归门禁（方向感知阈值+非零退出）、trace 落库——三个点都是"一等公民"而非拼装。
- **备选与放弃**：①Langfuse——tracing 强，但 judge 校准和门禁要么没有要么在付费层；②RAGAS——指标面向 RAG 问答对，Agent 任务成功率/工具正确性不对口；③pytest 断言硬编码——评测集要版本化和数据驱动。
- **后果**：5 个依赖、mock 模式 0 成本全链路；代价是生态集成自己做（Langfuse 导出列为扩展）。

## ADR-2 为什么 judge 必须带"校准"，校准为什么看 kappa 不看 accuracy

- **背景**：LLM-as-judge 本身是个模型——会偏严/偏松，不校准的打分是玄学。
- **决策**：校准四件套：golden 标注集 → accuracy + **Cohen's kappa** + 混淆矩阵 → 阈值扫描 → 修 rubric 回归（judge.py 校准模块 + selfeval 入口）。
- **备选与放弃**：①只看 accuracy——类别不平衡时虚高（30 条里 24 pass，全判 pass 也有 0.8）；②人肉抽查代替量化——不可复现。
- **后果**：真实校准故事：v1 kappa 0.510 → 只调阈值到 0.762（证明阈值非主因）→ 修订打分规则到 **0.889**（accuracy 0.967）；残余 1 例数字归因颠倒是规则 judge 盲区，如实记录。**kappa 修正了类别不平衡的假象，这就是不用 accuracy 的原因。**

## ADR-3 为什么门禁要"方向感知"

- **背景**：回归门禁最怕两种蠢：成功率涨了但 P95 也涨（要不要拦？）、噪声导致误拦。
- **决策**：gate.py 对每个指标声明方向（成功率/均分高好，P95/错误数低好），劣化量超阈值才 FAIL，exit 0/1/2 三态（放行/拦截/报告损坏）。
- **备选与放弃**：①全指标必须不降——噪声下永远在误拦；②只看单一总分——丢分丢在哪看不见。
- **后果**：演示数字：baseline 100% → 注入 8/30 错误后 judge 均分 4.32、通过率 73.33% → FAIL exit 1 拦截。阈值本身要随校准数据更新——阈值扫描的过拟合风险已在文档声明（30 条同源，生产需 200+ 独立标注）。

## ADR-4 为什么评测目标抽象成 callable/HTTP 双形态

- **背景**：被测对象五花八门：进程内函数、HTTP 服务、openai 兼容端点。
- **决策**：runner.py 的 target 抽象统一三种形态，trace 采集在 target 边界打 span（root→case→target.call→judge.score）。
- **备选与放弃**：①只支持 HTTP——进程内函数要起服务才能测，开发循环太慢；②只支持 callable——没法测已部署服务。
- **后果**：policy-compass/askbi 的 smoke 适配器各 10 条用例直接挂进来——评测平台"服务所有项目"的承诺落地。

## ADR-5 为什么用户模拟器要带"隐藏策略"

- **背景**：τ-bench 的洞察：只测单轮 QA 测不出 Agent 的策略遵循——用户得有"不会主动说但被问到必须答"的隐藏约束。
- **决策**：simulator.py = persona + HiddenPolicy + 多轮脚本；MockSimulator 确定性可测，LLMSimulator 留 provider 接口。
- **备选与放弃**：①固定脚本对话——测不到追问与坚持；②自由 LLM 扮演——不可复现、评分困难。
- **后果**：LLMSimulator 尚未真实回归（缺 key）——如实声明，接口已就位。
