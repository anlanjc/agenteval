# 真 LLM judge 校准（deepseek-v4-flash，30 条 golden）

- accuracy: 0.8000
- Cohen's kappa: 0.5455
- 混淆矩阵 (tp,fp,fn,tn): (18, 0, 6, 6)
- 对照 mock judge v2：accuracy 0.9667 / kappa 0.8889

## 分析（关键洞察）

1. **严格偏置跨模型复现**：真 judge fp=0 / fn=6——从不放过坏答案，但错杀 6 个好答案。这与 mock judge v1 的失败模式（kappa 0.51，同样偏严）完全同构。结论：**"judge 偏严"不是某个模型的偶然，是 LLM-as-judge 的系统性倾向**——这正是校准流程必须存在的原因，也是它可迁移的证据。
2. **口径警示**：mock v2 的 0.889 是在同 30 条用例上"校准拟合"出来的（规则修订用的就是这批数据），真 judge 的 0.546 是首次裸跑——两者不可直接比大小，**0.546 才是"新 judge 上线第一天的真实起点"**，下一步用它自己跑阈值扫描+修订 rubric（工具全部现成）。
3. 下一步：对真 judge 做阈值扫描（预期 kappa 显著回升，因为 fn=6 多半卡在阈值边缘）→ 修订 rubric → 二轮校准。

## 二轮校准（2026-10-28，scripts/judge_round2.py，用户已授权 ~¥0.2 API 花费）

### 方法

- 两轮各 30 次 `/chat/completions` 调用（temperature=0，deepseek-v4-flash-0731），共 60 次；
- 阈值扫描 3.0→4.5（步进 0.1，16 个点）——**扫描基于同一批 overall 分数离线判定，不重复调 LLM**：
  judge 输出的是连续分数，阈值只是判定规则——这是"调阈值免费、改 rubric 才花钱"的校准经济学；
- rubric 修订（judge.py，改动行见 PROGRESS 记录）：三条评分锚点放宽 + 系统提示加
  "长度/详略与补充性说明本身不扣分；先核对关键数值再评其余维度"——针对首轮 fn=6 的严格偏置，
  不向 golden 分布泄漏任何信息（修订依据是"长答案也可能是正确答案"的一般原则，不是数据集拟合的描述）。

### 结论与口径

1. **与 mock 故事相反：真 judge 的主因是阈值错配**——v1 只调阈值（4.0→3.0）就把 kappa 从 0.4444 拉到 0.8889（mock 里扫描只到 0.762）。跨模型校准的教训：mock 的归因结论不能外推。但 t=3.0 的操作点脆弱：贴着网格边缘、贴着 v1 的分数主体——分布一漂移就失效；
2. **rubric 修订的价值是把好判定点拉回默认阈值并修语义**：v2 @4.0 kappa 0.8889、FN 8→0，不再依赖边缘阈值；代价是 c-25（partial，60% 关键词命中）在 @4.0 被放过（fp 0→1）——mock 校准"分档过宽放过 partial"的教训在真 judge 上复现。扫描到 t=4.4 得 (24,0,0,6)，fp 归零；
3. **kappa=1.0 是 30 条拟合集的天花板读数，不是泛化声明**——二轮修订看过这 30 条的误差方向，与 mock v2 同属"校准拟合"；独立验证仍需 200+ 条未参与修订的人工标注（TODO 不变）；分数缓存只存系统临时目录，repo 内以本表逐条分数为准；
4. **judge 打分有运行间波动**：v1 @4.0 首轮记录 kappa 0.5455（fn=6）vs 本轮复测 0.4444（fn=8），fp=0 稳定、FN 集合在 6-8 间浮动（temperature=0 仍非严格确定）——单次裸跑数字不能当稳定基线，校准结论要配多次采样或观察窗；judge.py 的 rubric 原文/修订文差异见 PROGRESS 的改动行记录。

> 段序翻转 + pairwise A/B 翻转），本文件"运行间波动警示"的正式结论见

> 波动源是阈值边缘用例（c-23），多数决 0.8889（bootstrap 95% CI [0.6154, 1.0]）。
